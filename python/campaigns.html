Many datacubes#

A CubePipeline takes any number of cubes, each optionally with its own redshift, reddening, mask or wavelength scale, and fits them all in one run. On a machine with several GPUs, or one large GPU, the cubes run at the same time.

A list of cubes#

import brainsp

p = brainsp.CubePipeline("cubes/*.fits", redshift=0.03,
                         settings="my_settings.yaml", wavelength_scale="vacuum",
                         sn_mask=[3], fit_sn_threshold=3, output_dir="megacubes")
written = p.run()

Each cube with its own values#

per_cube gives each cube its own values, as a CSV file or as a list of dictionaries. The first column (or the target key) is the cube; every other column overrides one keyword of a stage for that cube alone.

target,redshift,ebv,mask file,wavelength scale,galaxy distance
manga-8626-12704.fits,0.0242,0.035,,vacuum,105.2
muse_ngc1068.fits,0.0038,0.029,ngc1068.sm,air,14.4

p = brainsp.CubePipeline(None, per_cube="targets.csv", sn_mask=[3],
                         fit_sn_threshold=3, settings="my_settings.yaml")

p = brainsp.CubePipeline(None, settings=s, sn_mask=[3], fit_sn_threshold=3,
                         per_cube=[{"target": "a.fits", "redshift": 0.024},
                                   {"target": "b.fits", "redshift": 0.031}])

The columns a table can carry are the keys of the enabled stages:

Stage

Keys

the fit

redshift, mask file, wavelength scale, galaxy distance, flux scale, population bins, sfr bins, fc bins, bb bins, flxobs step, batch size, and the extensions (hdu flux, hdu ivar, stat type, hdu mask)

dereddening

ebv, rv, law

S/N masks

thresholds, sn window, method, redshift

spatial binning

resample size

spectral binning

resample size

resolution

input type, input value, input ref wave, output type, output value, output ref wave

Butterworth filter

order, range

A column that no enabled stage reads is refused before the run starts, so a misspelt column never silently does nothing. Empty cells keep the pipeline’s value. On the command line, the same file is --table targets.csv.

How the cubes are run#

On one ordinary GPU, or on the CPU, the cubes run one after another in this process. On the CPU the worker pool stays warm from one cube to the next, so the workers start and load their compiled code once for the whole run (CPUs and GPUs).

With several GPU slots, the cubes are dealt out to the slots, each a process of its own on one GPU with its share of the card’s memory and of the CPU cores; a slot that finishes takes the next cube. By default there is one slot per GPU, and two on a card of 40 GB or more. Every megacube is bit for bit the one the sequential run writes, since each cube is fitted by the same code with the same settings.

One cube, several slots: the cube’s spaxels are spread over one worker per slot, while this process makes the cube-wide decisions on the CPU and writes the megacube. The result equals the single-GPU fit to rounding (5 × 10⁻⁵ at most, measured).

p.run(gpu_slots="auto")       # one per GPU, two on a 40 GB card
p.run(gpu_slots=4)            # four, dealt over the GPUs in turn
p.run(gpu_slots=1)            # one after another

On one ordinary GPU a second slot only makes each fit compile twice, so "auto" gives one and nothing changes. The gains come with more cards, or with a card large enough for two fits.

Note

JAX fixes its device the first time it is used in a process. A process that has already fitted on the GPU runs its later campaigns one cube after another; start a fresh process (or a script) to use several slots.

Skipping finished cubes#

overwrite=False skips every cube whose megacube already exists in output_dir, before its first stage runs. A long campaign that was stopped can therefore be restarted as it is, and continues where it stopped.
